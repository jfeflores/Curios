# Curios vault envelope v1

This describes the source-build format implemented in `Sources/CuriosCore/Vault.swift`. It is not an independent cryptographic audit or an E2EE synchronization protocol. Do not replace platform cryptographic primitives with new implementations.

## Frame and bounds

All integers in the binary prefix are unsigned 32-bit big-endian:

```text
8 bytes   ASCII CURIOSV1
4 bytes   UTF-8 JSON header length H
4 bytes   sealed body length B
H bytes   JSON header
B bytes   CryptoKit combined AES-GCM box: nonce[12] || ciphertext || tag[16]
```

The AES-256-GCM body's associated data is **the complete prefix and exact header bytes**, including both lengths. No trailing bytes are accepted. H is 1…16,384 bytes. B is 28…(64 MiB + 28) bytes. The total file is at most 64 MiB + 64 KiB; plaintext is at most 64 MiB. Bounds are checked before domain decoding and before password derivation. No compression is used.

The header has exactly these writer-defined fields (JSON strings use standard JSON escaping; Data fields use padded RFC 4648 Base64):

- `version`: integer `1`.
- `cipher`: string `AES-256-GCM`.
- `vaultID`: uppercase canonical UUID string, identifying a randomly generated vault.
- `generation`: uppercase canonical UUID string, identifying a key generation.
- `kind`: `database`, `recovery` (opaque preservation bytes), or `export`.
- `passphrase`: slot object with `salt`, `iterations`, `wrappedKey`.
- `recovery`: slot object with `salt`, `iterations`, `wrappedKey`.

Readers validate required field types/values and bounds. Unknown versions/suites are rejected, not treated as plaintext. JSONDecoder may ignore extra JSON keys; their bytes are still covered by the body authentication tag. They are not an extension-negotiation mechanism.

The writer uses compact UTF-8 JSON with lexicographically sorted ASCII keys and **without escaping solidus `/` characters** (`JSONEncoder` `.sortedKeys`, `.withoutEscapingSlashes`). Wrapper context values below are all ASCII, which makes the exact encoding reproducible across runtimes. Body readers authenticate the original header bytes rather than decode/reencode them.

## Key hierarchy

At enrollment:

- Random VMK: 32 bytes from `SecRandomCopyBytes`.
- Random recovery secret: independent 32 bytes.
- Random vault ID and generation UUIDs.
- Independent random 16-byte salts for each unlock slot.

Derive the 32-byte content key using HKDF-SHA-256:

```text
input key material = VMK
salt = UTF8(vaultID)
info = UTF8("Curios content key v1")
```

For the passphrase slot, use CommonCrypto PBKDF2-HMAC-SHA-256, 32-byte output, its 16-byte salt and **600,000 iterations**. Readers accept 600,000…2,000,000 iterations, rejecting values outside that range before deriving. Passphrases are exact UTF-8 bytes: no trimming, normalization or truncation. Maximum input is 1,024 UTF-8 bytes; new enrollment also requires at least 12 characters. The minimum length is not an entropy guarantee.

For the recovery slot, use HKDF-SHA-256:

```text
input key material = independent recovery secret
salt = recovery slot salt
info = UTF8("Curios recovery wrapping key v1")
output length = 32 bytes
```

Recovery slot `iterations` is `0`; HKDF is used with random high-entropy material, not a password.

Each slot's `wrappedKey` is a 60-byte combined AES-256-GCM box encrypting the 32-byte VMK. Its associated data is the compact/sorted/unescaped-solidus UTF-8 JSON object:

```text
{
  purpose: "Curios VMK wrapper v1",
  vaultID: <header vaultID>,
  generation: <header generation>,
  route: "passphrase" or "recovery",
  salt: <slot salt as Base64>,
  iterations: <slot iterations integer>
}
```

The notation above lists field meaning, not literal serialization: actual JSON keys/strings are quoted and sorted. Salts, route, vault identity and generation are authenticated. All AES-GCM encryptions use fresh random 96-bit nonces and full 128-bit tags generated by CryptoKit. Do not substitute a clock, fixed value or a counter vulnerable to restoration. A wrapper may be copied unchanged into multiple snapshots; that is not a new encryption using its nonce.

## Recovery representation and portability

The user recovery string is:

```text
CURIOS1-<64 uppercase hex digits for the 32-byte secret>-<8 uppercase hex checksum digits>
```

Checksum is the first four bytes of SHA-256(secret). Recovery parsing accepts case-insensitive hex and ignores whitespace/hyphens, with a 256-byte input bound. The checksum detects transcription mistakes, not malicious changes. The recovery string is never stored with the file; only its VMK wrapper is.

Passphrase and recovery slots are alternative access routes, not two-factor authentication. Recovery is as sensitive as the passphrase. The encrypted `.vault` enrollment snapshot includes the same unlock capability as the live store and intentionally preserves the enrollment state. Wrapper changes cannot revoke already copied old wrappers/ciphertext.

Portable export generates independent master/recovery material and a different vault ID. This release exposes **export-passphrase unlock only**; its unused random recovery secret is discarded and no export recovery kit is presented. Never give an export the live vault's master key or recovery capability. Imported data is reserialized under the destination vault's session, not adopted as its live identity.

## Verification and limits

Tests include NIST AES-256-GCM and platform PBKDF2 known answers, format/tamper/size/Unicode tests, encrypted persistence/migration/recovery, and an independent Python `cryptography`/OpenSSL reader for both wrapper routes and body authentication. The independent reader helped freeze solidus-escaping behavior before release; development-only pre-freeze synthetic fixtures are not a supported migration input.

Per-save nonces are random; no cryptographic anti-rollback, automatic VMK rotation or future-format negotiation is claimed. Very high-volume/long-lived automated usage needs a reviewed key-usage/rotation policy. Local encryption does not define server E2EE, device enrollment or conflict resolution. Any future format/key-management expansion needs versioning, interoperability vectors and security review.
